### 2.2 🔴 严重风险：缺少 CSRF 保护

**涉及文件**: 所有 API 路由文件

**发现**:
- 整个项目中**没有任何 CSRF 保护机制**
- 未找到 `csrf_token`、`x-csrf-token` 等相关代码
- 所有 API 请求仅依赖 Session Cookie 进行认证

**影响**: 攻击者可能通过跨站请求伪造攻击，在用户不知情的情况下执行操作（如生成图片扣费、积分转移等）。

**改进建议**:
1. 在关键操作 API（积分充值、积分转移、用户设置修改等）添加 CSRF token 验证
2. 考虑使用 `next-auth` 内置的 CSRF 保护或 `@edge-csrf/nextjs` 中间件
3. 对敏感操作使用 `SameSite=Strict` Cookie 策略

---

### 2.3 🟡 中危风险：缺少 Rate Limiting（速率限制）

**涉及文件**: 所有 API 路由文件

**发现**:
- 项目中**完全没有速率限制机制**
- 未找到 `middleware.ts` 文件或任何限流相关代码

**影响**:
- 攻击者可无限制调用 API（注册接口、图片生成接口等）
- 可能导致资源滥用、积分恶意消耗、API 费用暴增
- `/api/cron/cleanup` 等管理接口也没有任何保护

**改进建议**:
1. 对注册接口 `/api/auth/register` 添加 IP 速率限制（如 5次/小时）
2. 对图片/视频生成接口添加基于用户 ID 的速率限制
3. 对 cron 清理接口添加 IP 白名单或密钥认证
4. 推荐使用 `@upstash/ratelimit` 实现

---

### 2.6 🟡 中危风险：积分扣减操作不完全原子化

**涉及文件**:
- `src/services/credit.service.ts` - `deductCredits` 函数
- `src/app/api/generate/architecture/route.ts` - 架构生成接口
- `src/app/api/generate/agent-image/route.ts` - Agent图片生成

**发现**: `deductCredits` 使用 `findUnique` + `update` 两步操作，非原子性。`architecture` 和 `agent-image` 路由虽使用 `decrement` 但也未使用事务包裹整体流程。而 `decompose` 路由已正确使用了 `prisma.$transaction`，但未统一。

**影响**: 高并发场景下可能导致积分超扣（race condition）。

**改进建议**:
1. 统一使用 `prisma.$transaction` 包裹所有积分扣减操作
2. 参考 `credit.service.ts` 中 `transfer` 函数的正确实现

### 3.4 错误处理 - ⚠️ 中等

**正面发现**:
- API 路由均使用 try-catch 包裹
- 生成失败时状态更新为 `FAILED` 并记录错误

**存在问题**:
1. **错误信息泄露**: 直接返回原始 `err.message` 给客户端，可能暴露 API 调用细节和文件路径
2. **响应格式不统一**: 管理后台 API 用 `{ success: true, data }` 格式，其他 API 用 `success()` 工厂函数
3. **重复的错误处理逻辑**: `agent-image/route.ts` 和 `architecture/route.ts` 中存在重复代码

**改进建议**:
- 返回通用错误信息给客户端，详细错误记录在服务端日志
- 统一所有 API 使用 `success()`/`error()` 工厂函数

---

### 3.5 日志记录策略 - ⚠️ 较差

**存在问题**:
1. 过度使用 `console.log`（182处），影响性能和安全性
2. 无日志级别控制（debug/info/warn/error 未区分）
3. 日志中包含敏感信息（API 请求/响应体）
4. 无结构化日志，无法与日志聚合系统集成

**改进建议**:
- 引入 `pino` 或 `winston` 结构化日志库
- 根据环境变量控制日志级别
- 敏感数据脱敏后再记录
