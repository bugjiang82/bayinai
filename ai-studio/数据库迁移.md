## 1. 迁移前准备工作

### 1.1 环境检查清单

| 检查项 | 命令/方法 | 通过标准 |
|--------|-----------|----------|
| 目标数据库已安装 | `mysql --version` / `psql --version` | 显示版本号 ≥ 8.0 |
| 目标数据库服务运行中 | `systemctl status mysql` | `active (running)` |
| 数据库用户已创建 | `mysql -u <user> -p -e "SELECT 1"` | 连接成功 |
| 目标库已创建 | `SHOW DATABASES LIKE '<db_name>'` | 数据库存在 |
| ORM 工具支持目标数据库 | 检查 `prisma/schema.prisma` provider | provider 已配置 |
| 磁盘空间充足 | `df -h` | 可用空间 > 源库大小 × 3 |
| 应用可停机 | 与业务方确认停机窗口 | 获得授权 |

### 1.2 数据备份策略

```bash
# === 步骤 1: 停止应用服务，阻止新数据写入 ===
pkill -f "next dev" || systemctl stop <app-service>

# === 步骤 2: 备份源数据库（带时间戳，便于回滚） ===
BACKUP_FILE="dev.db.backup.$(date +%Y%m%d_%H%M%S)"
cp ./prisma/dev.db "./prisma/${BACKUP_FILE}"
echo "备份完成: ${BACKUP_FILE}"

# === 步骤 3: 备份环境配置文件 ===
cp .env .env.backup

# === 步骤 4: 备份 Schema 文件 ===
cp prisma/schema.prisma prisma/schema.prisma.backup

# === 步骤 5: 验证备份完整性 ===
ls -lh ./prisma/dev.db.backup.*
ls -lh .env.backup
```

**备份原则**：
- **3-2-1 原则**：至少 3 份副本，2 种不同介质，1 份异地存储
- **时间戳命名**：每次备份使用时间戳，确保可追溯
- **验证可恢复**：备份后立即验证文件完整性
- **保留周期**：至少保留 30 天，重大版本迁移永久保留

### 1.3 数据完整性基准验证

在迁移前记录源库各表行数，作为迁移后校验的基准：

```bash
sqlite3 ./prisma/dev.db "
SELECT 'Users' AS tbl, COUNT(*) FROM User
UNION ALL SELECT 'Generations', COUNT(*) FROM Generation
UNION ALL SELECT 'Agents', COUNT(*) FROM Agent
UNION ALL SELECT 'Templates', COUNT(*) FROM Template
UNION ALL SELECT 'CreditLogs', COUNT(*) FROM CreditLog
UNION ALL SELECT 'CreditPolicies', COUNT(*) FROM CreditPolicy;
" | tee /tmp/migration_baseline.txt
```

**输出示例**：
```
Users|2
Generations|30
Agents|5
Templates|8
CreditLogs|7
CreditPolicies|29
```

### 1.4 风险评估

| 风险类别 | 风险描述 | 概率 | 影响 | 缓解措施 |
|----------|----------|------|------|----------|
| 字段类型不兼容 | SQLite 弱类型 vs MySQL 强类型 | 高 | 高 | 提前分析字段类型，添加 `@db.*` 注解 |
| 大字段溢出 | 单字段超过目标类型容量 | 中 | 高 | 检查数据长度分布，使用 `MEDIUMTEXT` 等大类型 |
| 特殊字符转义 | 字段含换行符/引号/反斜杠 | 高 | 中 | 使用 JSON 导出方式，确保正确转义 |
| 外键约束冲突 | 导入顺序不当导致外键检查失败 | 中 | 中 | `SET FOREIGN_KEY_CHECKS=0` 在导入时关闭检查 |
| 时区偏移 | DateTime 字段在不同时区解释不同 | 低 | 中 | 使用 `FROM_UNIXTIME()` 明确转换 |
| 服务中断 | 迁移后应用无法连接新数据库 | 中 | 高 | 完整的回滚方案 + 分阶段验证 |

## 2. 迁移方案设计

### 2.1 工具选型对比

| 方法 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| **ORM Schema Push** | 使用 Prisma/Drizzle 等 ORM | 表结构自动同步，类型安全 | 不处理数据迁移 |
| **SQLite CLI 导出** | 小规模数据 (< 100MB) | 简单直接，无需额外依赖 | 字段分隔符可能被数据污染 |
| **JSON 导出模式** | 含特殊字符的数据 | 完美处理换行符、引号等 | 需要 Node.js 脚本处理 |
| **第三方 ETL 工具** | 超大规模 (> 1GB) | 专业、支持增量同步 | 配置复杂，学习成本高 |
| **数据库原生工具** | 同类型数据库迁移 | 原生支持，性能最优 | 不适用于跨类型迁移 |

**推荐方案**（基于 AI Studio 实战）：
- **表结构迁移**：使用 Prisma `db push`（自动处理类型映射和索引创建）
- **数据迁移**：使用 `sqlite3 -json` 导出 + Node.js 脚本转换 + MySQL CLI 导入
- **适用场景**：SQLite → MySQL 迁移，数据量 10MB-500MB

### 2.2 数据映射规则

#### 字段类型映射

| SQLite 类型 | MySQL 目标类型 | Prisma 注解 | 说明 |
|-------------|---------------|-------------|------|
| INTEGER | `INT` | 无需额外注解 | 自动映射 |
| REAL | `DOUBLE` | 无需额外注解 | 自动映射 |
| TEXT (短文本) | `VARCHAR(191)` | `@db.VarChar(191)` | 索引字段默认长度 |
| TEXT (URL) | `VARCHAR(2048)` | `@db.VarChar(2048)` | URL 字段 |
| TEXT (长文本) | `TEXT` (65KB) | `@db.Text` | 描述、提示词等 |
| TEXT (超长文本) | `MEDIUMTEXT` (16MB) | `@db.MediumText` | Base64 图片数据 |
| BOOLEAN | `TINYINT(1)` | 无需额外注解 | 自动映射 |
| DATETIME | `DATETIME(3)` | 无需额外注解 | 自动映射 |
| JSON 数组 | `TEXT` / `JSON` | `@db.Text` | MySQL 不允许 TEXT 有默认值 |

#### 关键映射规则

1. **移除 TEXT 列的默认值**：MySQL 不允许 `TEXT`/`BLOB` 列设置 `DEFAULT`
   ```prisma
   // 错误
   params String @db.Text @default("{}")
   // 正确
   params String @db.Text
   ```

2. **URL 字段长度评估**：如 `inputUrl` 可能存储 Base64 数据 URI（可达数百 KB），应使用 `@db.MediumText` 而非 `@db.VarChar(2048)`

3. **DateTime 时区处理**：SQLite 存储毫秒时间戳整数，MySQL 使用 `DATETIME` 类型，转换公式：
   ```sql
   FROM_UNIXTIME(millis_timestamp / 1000)
   ```

4. **Boolean 类型转换**：SQLite 存储 `0`/`1` 或 `true`/`false` 字符串，需统一转为 `0`/`1`

### 2.3 迁移顺序规划

遵循**依赖关系从根到叶**的顺序：

```
第 1 批：无外键依赖的基础表
  ├── User
  ├── Agent
  └── CreditPolicy

第 2 批：依赖基础表的业务表
  ├── Account (→ User)
  ├── Session (→ User)
  ├── Team (→ User)
  └── TeamMember (→ User, Team)

第 3 批：依赖业务表的详细表
  ├── Generation (→ User, Agent)
  ├── Template (→ User)
  ├── CreditLog (→ User)
  ├── CreditTransfer (→ User)
  └── CanvasProject (→ User)
```

**导入时关闭外键检查**：避免因导入顺序导致的外键约束错误

```sql
SET FOREIGN_KEY_CHECKS = 0;
-- ... 所有 INSERT 语句 ...
SET FOREIGN_KEY_CHECKS = 1;
```

### 3.2 阶段二：数据导出

**核心原则**：使用 JSON 格式导出，避免分隔符污染问题

```javascript
// migrate.js — 数据导出脚本
const { execSync } = require("child_process");
const fs = require("fs");

const sqliteDb = "./prisma/dev.db";

function sqliteJson(sql) {
  const result = execSync(
    `sqlite3 -json "${sqliteDb}" "${sql}"`,
    { encoding: "utf-8", maxBuffer: 200 * 1024 * 1024 }
  ).trim();
  return result && result !== "[]" ? JSON.parse(result) : [];
}

function getColumns(table) {
  return execSync(`sqlite3 "${sqliteDb}" "PRAGMA table_info('${table}')"`, {
    encoding: "utf-8",
  })
    .trim()
    .split("\n")
    .map((line) => {
      const parts = line.split("|");
      return { name: parts[1], type: parts[2] };
    });
}

function escapeValue(val, colName, colType) {
  if (val === null || val === undefined || String(val) === "") return "NULL";

  const str = String(val);

  // Boolean 转换
  if (colType.toLowerCase() === "boolean" || colName.startsWith("is")) {
    return str === "1" || str === "true" ? "1" : "0";
  }

  // 整数（含时间戳转换）
  if (/^-?\d+$/.test(str)) {
    const num = parseInt(str, 10);
    if ((colType.toLowerCase() === "datetime" || colName.endsWith("At")) && num > 1000000000000) {
      return `FROM_UNIXTIME(${num}/1000)`;
    }
    return str;
  }

  // 浮点数
  if (/^-?\d+\.\d+$/.test(str)) return str;

  // 字符串（转义单引号和反斜杠）
  const escaped = str.replace(/\\/g, "\\\\").replace(/'/g, "\\'");
  return `'${escaped}'`;
}

// 迁移顺序（按依赖关系）
const tables = [
  "User", "Agent", "CreditPolicy",       // 第 1 批
  "Account", "Session", "Team", "TeamMember", // 第 2 批
  "Generation", "Template", "CreditLog", "CreditTransfer", "CanvasProject", // 第 3 批
];

let output = "SET FOREIGN_KEY_CHECKS = 0;\n\n";

for (const table of tables) {
  const columns = getColumns(table);
  const colNames = columns.map((c) => c.name);
  const colList = colNames.map((n) => `\`${n}\``).join(", ");

  const rows = sqliteJson(`SELECT * FROM "${table}"`);
  if (rows.length === 0) continue;

  for (const row of rows) {
    const values = colNames.map((colName) => {
      const col = columns.find((c) => c.name === colName);
      return escapeValue(row[colName], colName, col ? col.type : "");
    });
    output += `INSERT INTO \`${table}\` (${colList}) VALUES (${values.join(", ")});\n`;
  }
  output += "\n";
}

output += "SET FOREIGN_KEY_CHECKS = 1;\n";
fs.writeFileSync("/tmp/mysql_import.sql", output, "utf-8");
```

## 4. 回滚机制

### 4.1 回滚触发条件

- 数据完整性校验失败（行数不匹配 > 5%）
- 应用启动后出现数据库连接错误
- 核心功能（登录、关键业务）不可用
- API 响应时间异常增长 > 10 倍

### 4.2 回滚操作步骤

```bash
# 步骤 1: 立即停止应用服务
pkill -f "next dev" || systemctl stop <app-service>

# 步骤 2: 恢复 .env 配置
cp .env.backup .env

# 步骤 3: 恢复 Schema 文件
cp prisma/schema.prisma.backup prisma/schema.prisma

# 步骤 4: 恢复数据库文件
cp prisma/dev.db.backup.<timestamp> prisma/dev.db

# 步骤 5: 重新生成 Prisma Client（如果 Schema 有变更）
cd /path/to/project
npx prisma generate

# 步骤 6: 重启应用
npm run dev

# 步骤 7: 验证功能
# 登录、核心业务功能测试
```

### 4.3 回滚时间目标

| 数据量 | 目标回滚时间 | 说明 |
|--------|-------------|------|
| < 100MB | < 5 分钟 | 手动操作即可 |
| 100MB - 1GB | < 15 分钟 | 需准备回滚脚本 |
| > 1GB | < 30 分钟 | 需自动化回滚方案 |

## 5. 性能优化策略

### 5.1 数据库层优化

#### 复合索引

在迁移完成后，为高频查询路径添加复合索引：

```prisma
model Generation {
  // ... 字段定义 ...

  // 单列索引（已存在）
  @@index([userId])
  @@index([status])
  @@index([createdAt])

  // 新增：复合索引
  @@index([type, status, createdAt])   // 覆盖：按类型+状态+时间筛选
  @@index([userId, createdAt])         // 覆盖：用户最近生成记录
}

model CreditLog {
  // ... 字段定义 ...

  @@index([userId, type])              // 覆盖：按用户+类型筛选
}
```

**复合索引设计原则**：
- 最左前缀原则：等值查询列在前，范围查询列在后
- 覆盖索引：索引包含 SELECT 所需的所有列
- 避免过多索引：每个 `INSERT`/`UPDATE` 都需要维护索引

#### MySQL 配置优化

```ini
# /etc/mysql/mysql.conf.d/mysqld.cnf

# InnoDB 缓冲池（可用内存的 50%-70%）
innodb_buffer_pool_size = 1G

# 排序缓冲区
sort_buffer_size = 4M

# 顺序读取缓冲区
read_buffer_size = 2M

# 最大连接数
max_connections = 100

# 字符集
character-set-server = utf8mb4
collation-server = utf8mb4_unicode_ci
```

**配置参数说明**：

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| `innodb_buffer_pool_size` | 物理内存的 50-70% | 越大，缓存命中率越高 |
| `sort_buffer_size` | 4M-8M | 每个排序连接分配，不宜过大 |
| `max_connections` | 100-200 | 根据并发量调整 |
| `character-set-server` | `utf8mb4` | 支持完整 Unicode（含 emoji） |

### 5.2 应用层优化

#### API 字段选择（减少数据传输）

```typescript
// 优化前：include 拉取所有字段（含大 TEXT）
const generations = await prisma.generation.findMany({
  where,
  include: { user: { select: { name: true, email: true } } },
  orderBy: { createdAt: "desc" },
  skip: (page - 1) * limit,
  take: limit,
});

// 优化后：select 仅选列表所需字段
const generations = await prisma.generation.findMany({
  where,
  select: {
    id: true,
    type: true,
    status: true,
    cost: true,
    createdAt: true,
    user: { select: { name: true, email: true } },
  },
  orderBy: { createdAt: "desc" },
  skip: (page - 1) * limit,
  take: limit,
});
```

**对比**：优化前拉取含 `prompt`、`params`、`inputUrl` 等大字段（每行可达 1MB+），优化后每行仅 ~200 字节，**数据传输量减少 99%+**。

#### Auth 缓存

```typescript
import { cache } from "react";

const cachedAuth = cache(() => auth());

export async function requireAdmin() {
  const session = await cachedAuth();
  // ...
}
```

**效果**：同一请求中多次调用 `requireAdmin()` 只执行一次 `auth()` 查询。

### 6.4 验收脚本

## 7. 常见问题与解决方案

### 7.1 字段类型不兼容

**问题**：`Error: BLOB, TEXT, GEOMETRY or JSON column 'params' can't have a default value`

**原因**：MySQL 不允许 TEXT/BLOB 类型列设置 `DEFAULT` 值

**解决**：移除 `@default` 注解
```prisma
// 修改前
params String @db.Text @default("{}")

// 修改后
params String @db.Text
```

### 7.2 数据超出字段长度

**问题**：`ERROR 1406 (22001): Data too long for column 'inputUrl' at row 1`

**原因**：目标列类型容量不足（如 `VARCHAR(2048)` 无法容纳 800KB 的 Base64 数据）

**解决**：
1. 检查源数据最大长度：`SELECT id, LENGTH(inputUrl) FROM Generation ORDER BY LENGTH(inputUrl) DESC LIMIT 5;`
2. 根据数据特征选择合适类型：
   - `< 65KB` → `TEXT` / `@db.Text`
   - `65KB - 16MB` → `MEDIUMTEXT` / `@db.MediumText`
   - `> 16MB` → `LONGTEXT` / `@db.LongText`

### 7.3 特殊字符导致导入失败

**问题**：`ERROR 1136 (21S01): Column count doesn't match value count at row 1`

**原因**：换行符、制表符等特殊字符在字段值中，导致行/列被错误拆分

**解决**：使用 JSON 格式导出（而非分隔符模式），JSON 天然支持转义
```bash
# 错误方式（分隔符可能被数据污染）
sqlite3 -separator "|" dev.db "SELECT * FROM Generation;"

# 正确方式（JSON 格式）
sqlite3 -json dev.db "SELECT * FROM Generation;"
```

### 7.4 外键约束冲突

**问题**：`ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails`

**原因**：导入数据时，父表数据尚未导入，但子表已尝试插入引用

**解决**：在导入脚本首尾包裹外键检查开关
```sql
SET FOREIGN_KEY_CHECKS = 0;
-- ... 所有导入语句 ...
SET FOREIGN_KEY_CHECKS = 1;
```

### 7.5 Prisma Client 缓存问题

**问题**：修改 `.env` 后应用仍连接旧数据库

**原因**：Prisma Client 在生成时缓存了数据库连接信息

**解决**：修改 `.env` 后必须重新生成
```bash
npx prisma generate
```

### 7.6 时区偏移

**问题**：迁移后日期时间显示偏移 8 小时

**原因**：SQLite 存储毫秒时间戳，MySQL 的 `DATETIME` 类型受时区影响

**解决**：使用 `FROM_UNIXTIME()` 明确转换，并确保 MySQL 时区设置正确
```sql
-- 转换毫秒时间戳为 DATETIME
FROM_UNIXTIME(millis_timestamp / 1000)

-- 检查 MySQL 时区
SELECT @@global.time_zone, @@session.time_zone;
```

## 8. 附录：实战案例

### 8.1 AI Studio 项目迁移总结

**项目环境**：
- Ubuntu 24.04.4 LTS
- Next.js 16.2.4 + Prisma 5.22
- 源库：SQLite 16MB（7 张表，82 条记录）
- 目标库：MySQL 8.0.45

**迁移耗时**：

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 停服备份 | 1 分钟 | 停止服务 + 备份 SQLite |
| Schema 推送 | 2 分钟 | 清空旧表 + `prisma db push` |
| 数据导出导入 | 3 分钟 | JSON 导出 + SQL 导入 |
| 环境切换 | 1 分钟 | `.env` 修改 + `prisma generate` |
| 性能优化 | 5 分钟 | 复合索引 + my.cnf + API select |
| 功能验证 | 5 分钟 | 12 页全量验证 |
| **总计** | **17 分钟** | 含问题排查和修复 |

**遇到的问题及解决**：

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| `inputUrl` 导入失败 | VARCHAR(2048) 无法容纳 Base64 数据 | 改为 `MEDIUMTEXT` |
| 换行符导致导入失败 | `errorMsg` 字段含多行文本 | 改用 JSON 格式导出 |
| 首次导入数据不完整 | 部分报错后数据部分导入 | 先 `TRUNCATE` 再重新导入 |

**优化效果**：

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 内容管理页加载 | 3-5s | 0.16s | **95%+** |
| 积分日志 API | N/A | 0.09s | 极快 |
| 管理后台首页 | 3-5s | 0.15s | **95%+** |
